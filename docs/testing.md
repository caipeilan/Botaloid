# 测试

在项目根目录运行，使用安装了项目依赖的 Python 环境。

## 本地自动检查

```sh
python -m unittest discover -s tests
node --test tests/test_web.mjs
```

Python 测试覆盖检索、原文出处核对、曲库快照发布、模型协议与管理接口。需要实际模型的检查默认跳过。

上下文测试覆盖历史消息条数的默认值 6、保存与运行环境切换、0～100 的整数校验、聊天服务传参，以及规划和选句使用配置条数并保留歌词出处等历史元数据。每条历史消息向模型提供最多 350 字符。

普通聊天及其保底回复按表达需要选择段数，成功回复至少包含一个片段，段数以本轮候选为界。测试覆盖四段及全部候选、同曲不同位置、重复和重叠位置去重、多段历史回传、第四首及以后的曲目指代、无效编号和空选。每个候选最多显示四个短句，可用 `start`（从 1 开始）和 `count` 选择其中的连续范围；提取原文和返回出处均使用实际选择的位置。测试覆盖跳过残尾、非默认起点、越界、布尔值及偏移后的重叠去重。

普通检索和人工兜底按实际分句原文识别近期使用情况，跨原始歌词行组合的句子也会识别。有未用过的起句时，常规候选池优先提供这些候选；全部起句均已用过时保留原候选用于兜底。用户明确要求复述原句时，规划阶段用 `repeat=true` 保留已用候选；追问或批评重复不视为复述。比较保留问句等标点。选句阶段收到近期已引用的句子编号，以及覆盖候选各句的原始歌词行译文（最多 320 字符）。

`tests/test_fallback.py` 覆盖成功即停、无候选与选句否决后的换方向、失败记录传递、重复方向去重、全曲库保底优先于人工兜底、等待预算、接口错误终止，以及保底回复与查找命中的区别。另覆盖当前追问更新检索方向、规划目标作为可修正的检索参考、保底可回应新动作，以及人工兜底全部近期使用过时仍允许接话。

聊天最多进行首轮、两次换方向和全曲库保底四轮检索。全曲库保底仍未选出合适台词时，才检索人工标记并增加一次选句。完整流程最多四次规划、五次选句，共九次模型调用；无候选时省略选句，成功即停止。网页端各次调用共用本轮等待预算。接唱已核验到曲末时正常结束。

程序向两个阶段提供 `retries_left`，四轮分别为 3、2、1、0。候选牵强时，选句可以用 `choices=[]` 退回整批候选，`check` 说明缺口；下一轮规划据此换角度。额度为 1 时提示再次退回将进入保底；额度为 0 时停止重新规划，全库保底空选后仅尝试人工兜底，仍无合适候选则返回 `no_match`。测试覆盖提前进入保底时归零、人工兜底沿用零额度及最终空选终止。回退额度不改变原文、描述对象和明确条件的要求。

提示词位于 `botaloid/prompts.py`，按任务说明与输出格式分开维护。规划根据当前消息和历史生成检索方向；选句读取当前原话、历史、候选和明确条件，`reply_goal` 作为可修正的检索参考。规划目标用于检索及本轮失败记录，不会跨轮保存为待答问题。歌词组合由选句阶段决定，程序负责候选编号、连续范围、原文出处、重复位置和启用状态核验。

模型规划兼容扁平的 `directions`，转为每组三词、最多四组；已分组方向按同样容量截取，非字符串仍报字段路径。内部 `check` 超过 160 字符时截取，不丢弃有效选句。必要字段无效时，错误标出规划或选句阶段及字段位置。

规划默认温度为 0.2，选句为 0.55，用户显式设置时同时覆盖。Ollama 默认输出预算为规划 512 token、选句 1024 token；用户显式设置时覆盖两个阶段。兼容 API 默认不发送输出 token 上限，只有用户显式设置时才发送。

## 实际模型检查

这些检查使用「模型设置」中已配置的接口，会产生实际调用及对应费用。测试素材为自写短句，不需要个人曲库。

Windows PowerShell：

```powershell
$env:BOTALOID_TEST_MODEL = '1'
python -m unittest tests.test_model_behavior -v
Remove-Item Env:BOTALOID_TEST_MODEL
```

Linux / macOS：

```sh
BOTALOID_TEST_MODEL=1 python -m unittest tests.test_model_behavior -v
```

`tests/fixtures/selection_cases.json` 包含 26 种选句场景，核对实际引用的候选、顺序和连续范围。覆盖身份、称呼、描述对象、陪伴、道歉、反问、递减回退、自然保底、重复接法、截短改变立场的尾句、跳过残尾、原因追问、四段互补及明确复述。固定候选池按本轮剩余额度允许重试，否决理由传给下一次选句。模型自报的解释不能代替实际选句结果。

`tests/fixtures/conversation_cases.json` 包含四种情景：拒绝安慰后追问关系、追问没能对谁说出口、关系与聊天内容等四项互补信息，以及明确复述。测试在临时曲库中完成实际规划、检索和选句，核对复述标记和最终原句。失败时输出规划和选择结果用于定位。

同一测试模块另覆盖找歌、查看下一句歌词、接唱、限定作者推荐和英语原文回复，核对实际意图、曲目、原句及语言条件。

## 真实聊天对照

使用脱敏的真实对话比较提示词，双方使用同一模型配置、同一曲库、同一语言和历史条数，并选择明确的提交作为基线：

1. 固定历史：每个检查点都输入记录中相同的前文，比较当前实现与基线。
2. 连续对话：每个版本从空历史开始，依次发送相同用户消息，并使用该版本上一轮实际返回的原句、语气和出处继续下一轮。
3. 逐项检查回应对象、是否承接最新问题、新动作是否改变回应、同义堆叠、问句复述、残尾和 `no_match`，同时记录调用次数和耗时。

真实聊天记录、对照结果和日志作为本地排查资料保存。状态为 `ok` 只表示返回了合法歌词，不能代替对回复含义和上下文的判断。
